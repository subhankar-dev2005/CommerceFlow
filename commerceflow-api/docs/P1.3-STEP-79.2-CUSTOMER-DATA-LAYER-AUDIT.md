## 2. Login Hardening

### `[EXISTING]`
Previously, `login-user.controller.js` verified user existence via `User.findOne({ email }).select('+password')` and verified password hash via `bcrypt.compare(password, user.password)`. If password was valid, it immediately invoked `generateToken(...)` and returned `200 OK`. It did not check `user.isActive`.

### `[CHANGED]`
The controller now performs an explicit account status check immediately following password validation:
```javascript
const isPasswordValid = await bcrypt.compare(password, user.password);

if (!isPasswordValid) {
  throw new AppError("Invalid email or password", 401, [], "INVALID_CREDENTIALS");
}

if (user.isActive === false) {
  throw new AppError("User account is deactivated", 401, [], "ACCOUNT_DEACTIVATED");
}

const token = generateToken({
  userId: user._id.toString(),
  email: user.email,
  role: user.role
});
```

### Security Properties:
- **Timing and Account Enumeration Defense:** Password verification precedes the `isActive` check. Attackers cannot probe whether an email is registered or whether an account is active or inactive by submitting guessed credentials; invalid credentials consistently yield `401 INVALID_CREDENTIALS`.
- **Role Neutrality:** The status guard applies universally to all roles (`customer` and `admin`).
- **No Token Generation:** `generateToken` is never called for inactive accounts.
- **Contract Consistency:** The error code `ACCOUNT_DEACTIVATED` and message `"User account is deactivated"` precisely match `src/common/middleware/auth.middleware.js`.

## 4. JWT Behavior

1. **At Login:** No JWT token is created or returned if `isActive === false`.
2. **On Subsequent Requests (`authMiddleware`):** Every authenticated request looks up `User.findById(decoded.userId)`. If an active token is presented but `user.isActive === false`, the request is immediately blocked with `401 ACCOUNT_DEACTIVATED`.
3. Thus, account deactivation is effective **instantaneously** both at login and across any active sessions.

## 6. Index Rationale & Query Support

### Index 1: `{ role: 1, createdAt: -1 }`
- **Query Supported:** `GET /api/v1/admin/customers?page=1&limit=10&status=all`
- **Query Filter:** `{ role: 'customer' }` sorted by `{ createdAt: -1 }`
- **Benefit:** Allows index-covered sort without performing an in-memory collection scan (`COLLSCAN` / memory sort). Prevents memory threshold errors on large user datasets.

### Index 2: `{ role: 1, isActive: 1, createdAt: -1 }`
- **Query Supported:** `GET /api/v1/admin/customers?page=1&limit=10&status=active` or `status=inactive`
- **Query Filter:** `{ role: 'customer', isActive: true|false }` sorted by `{ createdAt: -1 }`
- **Benefit:** Combines equality filtering on both role and active state with index-ordered traversal of creation date.

---

## 7. Duplicate Index Check

- Verified via `User.schema.indexes()`:
  - `{ email: 1 }` is an independent single-field unique index.
  - `{ role: 1, createdAt: -1 }` prefix is `role`, which does not overlap with `email`.
  - `{ role: 1, isActive: 1, createdAt: -1 }` has intermediate field `isActive`, meaning `{ role: 1, createdAt: -1 }` cannot be satisfied by `{ role: 1, isActive: 1, createdAt: -1 }` for queries where `isActive` is omitted (due to MongoDB index prefix rules).
  - No redundant or duplicate indexes exist.
