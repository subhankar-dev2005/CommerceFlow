# P1.6 — Product Variants & End-to-End Variant Commerce Pipeline

## 1. Purpose

The P1.6 milestone family establishes first-class product variant capabilities and guarantees end-to-end variant lifecycle integrity across the entire CommerceFlow commerce pipeline.

Product variants enable products to offer multiple purchasing options (such as size, color, or material) while maintaining strict catalog, cart, checkout, inventory, and cancellation consistency. Specifically, P1.6 delivers:
- Unique variant identification (`variantId`)
- Global stock keeping unit (`SKU`) management
- Dynamic variant attributes (`attributes` map)
- Variant-level price overrides
- Variant-level stock tracking and aggregate product stock synchronization
- Continuous variant identity propagation from catalog through cart to orders
- Transactional and atomic inventory integrity throughout order checkout, cancellation, and compensation restoration flows

---

## 2. Canonical Identity Flow

Variant identity is preserved deterministically at every phase of the commerce lifecycle:

```text
Product (Catalog)
  └──> Cart Line Item
        └──> Order Item Snapshot
              └──> Atomic Inventory Reservation
                    └──> Cancellation / Compensation Inventory Restoration
```

### Identity Tuples

1. **Product Identity**: `(product._id, variantId)`
   - Identifies a specific variant subdocument embedded within a parent Product document.
   - For simple (non-variant) products, `variantId` is `null` or omitted.

2. **Cart Line Identity**: `(productId, variantId)`
   - Cart lines are uniquely keyed by the compound tuple `(productId, variantId)`.
   - Adding the same product with different `variantId` values results in distinct cart items. Adding the same product with the identical `variantId` increments line quantity.

3. **Order Snapshot Identity**: `(productId, variantId, sku)`
   - At checkout, the order item captures an immutable point-in-time snapshot of the purchased variant, including `productId`, `variantId`, `variantName`, `sku`, `price`, and `quantity`.
   - Historical orders remain accurate even if parent product attributes, prices, or variants are modified or removed later in the catalog.

## 3. SKU Architecture

Stock Keeping Units (SKUs) are critical identifiers for commerce operations and inventory tracking. The system enforces the following SKU architecture:

- **Global Uniqueness**: SKUs are strictly unique catalog-wide across all products and variants.
- **Normalization**: SKUs are automatically trimmed of whitespace and converted to uppercase (`normalizeSku(sku)`: uppercase + trimmed alphanumeric, hyphen, underscore).
- **SkuRegistry as Uniqueness Authority**:
  - Catalog-wide unique SKU validation cannot be safely enforced solely via a MongoDB unique multikey index on embedded variant arrays (`variants.sku`) due to MongoDB multikey sparse indexing constraints on arrays.
  - A dedicated `SkuRegistry` collection (`sku-registry.model.js`) serves as the authoritative uniqueness barrier, backed by a unique index on `{ sku: 1 }`.
  - `Product.variants.sku` is preserved as an embedded attribute for query convenience but is **not** relied upon as the global uniqueness authority.
- **Atomic Concurrency**: Simultaneous attempts to register or reserve duplicate SKUs are caught and rejected atomically via MongoDB unique constraint enforcement in `SkuRegistry.create` (throwing `SKU_ALREADY_EXISTS` / HTTP 409).
- **Legacy Compatibility**: Legacy simple products without variants remain valid without requiring mandatory registry entries unless assigned an explicit SKU.

## 4. Inventory Architecture

Inventory is tracked at both the individual variant level and the parent product aggregate level:

- **Simple Product Inventory**:
  - Tracked via `product.stock`.
- **Variant Product Inventory**:
  - Each variant maintains independent stock: `variant.stock`.
- **Variant Product Aggregate**:
  - The parent product stock represents the sum of all active variant stock:
    $$\text{product.stock} = \sum \text{variant.stock}$$
  - Both levels are decremented during reservation and incremented during restoration to keep aggregate queries and variant stock completely consistent.

### Eventual Atomic Reservation Target (P1.6.3)

During order checkout, inventory reservation for variant items must be atomic to prevent race conditions and overselling:

```javascript
Product.findOneAndUpdate(
  {
    _id: productId,
    "variants.variantId": variantId,
    "variants.stock": { $gte: quantity }
  },
  {
    $inc: {
      "variants.$.stock": -quantity,
      stock: -quantity
    }
  }
)
```

### Eventual Atomic Restoration Target (P1.6.4 / P1.6.5)

During customer/admin cancellation or checkout compensation, stock is restored to both the specific variant and the parent aggregate:

```javascript
Product.findOneAndUpdate(
  {
    _id: item.product,
    "variants.variantId": item.variantId
  },
  {
    $inc: {
      "variants.$.stock": item.quantity,
      stock: item.quantity
    }
  }
)
```

> [!NOTE]
> The above queries define the architectural targets for later checkpoints (P1.6.3–P1.6.5) and are **not** implemented in this baseline checkpoint.

## 5. Backward Compatibility & System Invariants

The variant architecture is strictly backward-compatible with all existing CommerceFlow functionality:

- **Simple Products**: Products without variants continue to operate unchanged. Their stock remains tracked directly via `product.stock`.
- **Simple Cart Operations**: Cart operations for products without variants continue to function as before. `variantId` is `null` or omitted.
- **Variant Validation**: Supplying a `variantId` for a simple product, or omitting `variantId` when adding a variant-enabled product to cart, remains invalid and is rejected with appropriate validation errors.
- **Order Deserialization**: Existing orders without variant metadata deserialize `variantId`, `variantName`, and `sku` as `null` without error.
- **Payment Pipeline**: Payment calculation continues to be based on `order.total` and server-calculated financial totals; payment flows (Razorpay) are agnostic to variant presence.
- **Cancellation Lifecycle Invariants**: All cancellation state machine guarantees, actor validation, idempotency guards, and single-winner concurrency rules established in P1.5 (P1.5.6) remain completely intact.

## 8. Dependencies & Hardened Invariants

### Dependency on P1.5 (Order Cancellation Lifecycle)

P1.6 inventory restoration (checkpoints P1.6.4 and P1.6.5) directly builds upon the hardened order cancellation lifecycle established in P1.5 (specifically P1.5.6):

- **Single-Winner Concurrency**: Only one cancellation request (customer or admin) may successfully transition an order to `cancelled` and trigger inventory restoration.
- **Idempotency**: Duplicate cancellation attempts must be safely rejected without duplicate stock increments.
- **Actor Metadata**: Cancellation actor, timestamp, and reason tracking must remain intact.
- **Restoration Keys**: Restart-safe compensation via unique `restorationKey` tracking must be preserved when handling variant items.
