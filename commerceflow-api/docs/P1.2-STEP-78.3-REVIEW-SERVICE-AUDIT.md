## 1. Purchase Verification Implementation

The purchase verification logic is implemented in `src/modules/reviews/review.service.js` under the function `findQualifyingOrder(userId, productId)`.

### Operational Flow
1. **Identifier Validation:**
   - Validates that `userId` and `productId` are non-empty 24-character hexadecimal strings matching `/^[0-9a-fA-F]{24}$/`.
   - Rejects malformed IDs immediately without querying the database, returning `{ eligible: false, order: null }`.
2. **Server-Side Discovery Query:**
   - Executes an authoritative database query on the `Order` collection:
     ```javascript
     const qualifyingOrder = await Order.findOne({
       user: new mongoose.Types.ObjectId(userId),
       status: "delivered",
       "payment.status": "paid",
       "items.product": new mongoose.Types.ObjectId(productId)
     })
       .sort({ createdAt: -1 })
       .lean();
     ```
3. **Return Contract:**
   - **Eligible:** `{ eligible: true, order: qualifyingOrder }`
   - **Ineligible:** `{ eligible: false, order: null }`
   - Does not throw application or HTTP errors for normal ineligibility, allowing future controllers to render user-friendly 403 or eligibility responses cleanly.

## 2. Exact Qualifying-Order Rule

A customer is considered a **Verified Buyer** eligible to review a product if and only if all four conditions are met simultaneously:

$$\text{Eligible} \iff (\text{Order.user} = \text{userId}) \land (\text{Order.status} = \text{"delivered"}) \land (\text{Order.payment.status} = \text{"paid"}) \land (\text{productId} \in \text{Order.items[].product})$$

### Specific Status Invariants
- `status`: Must be strictly `"delivered"`.
  - Non-qualifying states: `"pending"`, `"confirmed"`, `"processing"`, `"shipped"`, `"cancelled"`.
  - Prohibits premature reviews before physical receipt and protects against review spamming on orders that may yet be cancelled.
- `payment.status`: Must be strictly `"paid"`.
  - Non-qualifying states: `"pending"`, `"failed"`, `"refunded"`.
- `items.product`: Verifies product membership in the immutable historical item snapshot.

---

## 3. Multiple-Order Behavior

If a customer has purchased the same product across multiple separate orders (e.g., reorders over several months/years):
- The query applies `.sort({ createdAt: -1 })`.
- This **deterministically selects the most recent qualifying delivered order**.
- The unique compound index on Review (`{ user: 1, product: 1 }`, implemented in Step 78.2) guarantees that repeat purchases do not create duplicate review records or artificially inflate rating counts. The user maintains and edits their existing single review.

---

## 4. Inactive-Product Behavior

- In CommerceFlow, when a product is marked inactive (`isActive: false`), historical orders in the database remain unmodified.
- `findQualifyingOrder` queries the immutable `Order` historical record (`order.items.product`), ensuring a customer who purchased a product that was later retired or made inactive still legitimately qualifies to review their experience.
- The product's active/inactive visibility on the storefront is handled at the route/catalog layer, preserving historical customer rights.

## 5. Rating Aggregation Implementation

Rating aggregation is implemented in `src/modules/reviews/review.service.js` under `recalculateProductRating(productId)`.

### Operational Flow
1. **Validation & Product Existence:**
   - Validates `productId` format; throws `400 INVALID_ID` if malformed.
   - Checks if `Product.exists({ _id: productObjectId })`. Throws `404 PRODUCT_NOT_FOUND` if the product does not exist, preventing orphan calculations.
2. **MongoDB Aggregation Pipeline:**
   - Executes a memory-efficient database aggregation on `Review`:
     ```javascript
     const stats = await Review.aggregate([
       {
         $match: {
           product: productObjectId,
           status: "published"
         }
       },
       {
         $group: {
           _id: "$product",
           ratingCount: { $sum: 1 },
           ratingAverage: { $avg: "$rating" }
         }
       }
     ]);
     ```
3. **Status Filtering:**
   - Strictly filters `{ status: "published" }`.
   - Hidden (`"hidden"`) and flagged (`"flagged"`) reviews are completely excluded from both `ratingCount` and `ratingAverage`.
4. **Empty State Handling:**
   - If no published reviews exist (or the only published review is hidden/deleted), the pipeline returns an empty array `[]`.
   - The service resets metrics cleanly to `ratingAverage: 0` and `ratingCount: 0`.

## 7. Atomic Update Strategy

- `recalculateProductRating` executes an atomic `$set` update on the `Product` document:
  ```javascript
  const updatedProduct = await Product.findByIdAndUpdate(
    productObjectId,
    {
      $set: {
        ratingAverage,
        ratingCount
      }
    },
    { new: true }
  );
  ```
- **Why `$set` over `$inc`:**
  On standalone MongoDB without multi-document transactions, counter increment deltas (`$inc`) are prone to permanent drift if a crash or concurrent request interrupts execution. An authoritative recalculation pipeline paired with `$set` is fully self-healing and crash-consistent.

---

## 8. Precision & Rounding Strategy

- To prevent floating-point anomalies (e.g., `4.333333333333333`), the service rounds the average rating deterministically to two decimal places:
  ```javascript
  ratingAverage = Math.round(stats[0].ratingAverage * 100) / 100;
  ```
- Examples verified in tests:
  - $5 + 4 + 3 \implies 4.0$
  - $5 + 4 \implies 4.5$
  - $5 + 4 + 4 \implies 4.33$

---

## 9. Index Decisions

- **Review Collection:**
  - Compound unique index: `{ user: 1, product: 1 }` (enforces single review invariant).
  - Query index: `{ product: 1, status: 1, createdAt: -1 }` (supports review listing and aggregation).
- **Order Collection:**
  - Existing indexes: `{ user: 1, createdAt: -1 }` and `{ user: 1, status: 1, createdAt: -1 }`.
  - The query `Order.findOne({ user, status: "delivered", ... }).sort({ createdAt: -1 })` leverages the existing compound index on `user` and `status` efficiently. No speculative new indexes were added to `Order`.

---

## 10. Concurrency & Idempotency Behavior

- Multiple concurrent recalculations on the same product result in identical `$set` payloads.
- Running `recalculateProductRating` repeatedly without underlying review changes produces the exact same numeric metrics, demonstrating complete idempotency.
