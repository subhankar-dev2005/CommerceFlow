## 1. Endpoint Specification

- **Method:** `PATCH`
- **Path:** `/api/v1/admin/customers/:customerId/status`
- **Description:** Allows an authenticated administrator to safely and atomically activate or deactivate a customer account (`isActive: true | false`).
- **Request Body:**
  ```json
  {
    "isActive": false
  }
  ```

- Inactive administrators cannot invoke the route (blocked at `authMiddleware` with `401 ACCOUNT_DEACTIVATED`).
- Reuses the existing authentication and authorization architecture without introducing secondary mechanisms.

## 3. Strict Validation Architecture

Implemented in `src/modules/users/admin-customer.validator.js` via `updateCustomerStatusSchema`:

- **Path Parameters (`params`):**
  - `customerId`: Validated as a strict 24-character hexadecimal MongoDB ObjectId regex (`/^[0-9a-fA-F]{24}$/`). Malformed parameters fail fast before querying the database, returning `400 VALIDATION_ERROR`.
- **Request Body (`body`):**
  - `isActive`: Required boolean (`z.boolean({ required_error: ..., invalid_type_error: ... })`).
  - Rejects string literals `"true"` and `"false"`.
  - Rejects numbers (`0`, `1`), `null`, `arrays`, or object values.
  - Rejects missing `isActive`.
  - `.strict("Unrecognized fields in request body")`: Rejects extra/unknown fields (e.g. attempting to supply `role: "admin"`).
- **Status:** `[VERIFIED]`

## 4. Customer-Only Protection & Role Isolation

- **Target Query Filter:**
  The update operation is strictly scoped to:
  ```javascript
  {
    _id: customerId,
    role: "customer"
  }
  ```
- **Admin Target Isolation:**
  If an administrative account ID is passed as `:customerId`, the filter matches zero documents, returning `404 CUSTOMER_NOT_FOUND`.
- **Non-Enumeration:** Nonexistent IDs and administrator IDs return the exact same `404 CUSTOMER_NOT_FOUND` response with identical error envelopes, preventing account enumeration or role probing.
- **Status:** `[VERIFIED]`

---

## 5. Self-Deactivation Protection

- An administrator must never inadvertently or maliciously deactivate their own administrative account.
- Handled at two defence-in-depth levels:
  1. **Pre-check:**
     ```javascript
     if (req.user && req.user._id && req.user._id.toString() === customerId) {
       throw new AppError("Customer not found", 404, [], "CUSTOMER_NOT_FOUND");
     }
     ```
  2. **Query scope:** The atomic update filter includes `role: "customer"`. Because the acting admin has `role: "admin"`, the filter would also match zero documents.
- Both layers return `404 CUSTOMER_NOT_FOUND`.
- **Status:** `[VERIFIED]`

## 6. Atomic Mutation & Concurrency Safety

- Uses an atomic MongoDB operation `User.findOneAndUpdate`:
  ```javascript
  const customer = await User.findOneAndUpdate(
    {
      _id: customerId,
      role: "customer"
    },
    {
      $set: { isActive }
    },
    {
      new: true,
      runValidators: true
    }
  )
    .select("_id name email role isActive createdAt updatedAt")
    .lean();
  ```
- **Zero Race Conditions:** Avoids `findOne()` followed by `save()` (read-then-save anti-pattern).
- **Zero Field Creep:** Only `$set: { isActive }` is updated. `role`, `email`, `name`, `password`, and `passwordHash` are untouched.
- **Status:** `[VERIFIED]`

## 7. Idempotency

- Setting a customer account to its existing active state succeeds normally with HTTP 200:
  - `active -> active`: 200 OK
  - `inactive -> inactive`: 200 OK
  - `active -> inactive`: 200 OK
  - `inactive -> active`: 200 OK
- No conflict (`409`) or error is thrown when the desired state matches the current state.
- **Status:** `[VERIFIED]`

## 9. Commerce Data Preservation

Customer activation/deactivation alters **only** the customer's `User.isActive` field. It does not delete, mutate, or cascade into:
- Orders (`Order` collection)
- Order items, financials, prices, and totals
- Payment records & Razorpay transactions
- Shipment records
- Customer addresses (`Address` collection)
- Product reviews & ratings (`Review` collection)
- Customer wishlist (`WishlistItem` collection)
- Customer shopping cart (`Cart` collection)
- Product inventory / stock levels
- **Status:** `[VERIFIED]`

## 10. Login & Session Integration

- **Login Hardening (Step 79.2 Integration):**
  When an account is deactivated (`isActive: false`), subsequent login attempts through `POST /api/v1/users/login` are immediately blocked with `401 ACCOUNT_DEACTIVATED` ("User account is deactivated"). No JWT is issued.
- **Immediate Session Invalidation:**
  Because the application uses stateless JWT authentication paired with `authMiddleware` which resolves the user record via `User.findById` on each authenticated request:
  - An already-issued token for a deactivated customer is rejected on the very next request with `401 ACCOUNT_DEACTIVATED`.
  - Reactivating an account allows the customer to authenticate immediately.
- **Status:** `[VERIFIED]`
