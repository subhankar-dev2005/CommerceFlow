## 1. Executive Summary

This audit assesses the production requirements, security implications, data-flow models, and performance considerations for introducing **Admin Customer Management (P1.3)** into CommerceFlow.

### Key Conclusions:
- `[EXISTING]` The `User` model (`src/modules/users/user.model.js`) already contains `isActive: { type: Boolean, default: true }`, `role: { type: String, enum: ['customer', 'admin'], default: 'customer' }`, and timestamps (`createdAt`, `updatedAt`).
- `[EXISTING]` The centralized authentication middleware (`src/common/middleware/auth.middleware.js`) already checks `User.findById(decoded.userId)` on every authenticated request and explicitly rejects deactivated accounts with `401 Unauthorized` (`ACCOUNT_DEACTIVATED`). Thus, deactivating a customer invalidates existing JWT sessions on their very next request without requiring token blacklists or distributed state stores.
- `[EXISTING / DEFECT IDENTIFIED]` The login controller (`src/modules/users/login-user.controller.js`) verifies credentials but currently omits an explicit `user.isActive === false` check. A deactivated customer could currently obtain a new JWT upon login (though their subsequent requests would be blocked by `authMiddleware`). Fixing this in Step 79.2 / 79.5 is `[REQUIRED]`.
- `[REQUIRED]` Strict Admin Self-Protection & Role Guards: Administrators must never be permitted to deactivate themselves or another administrator account (`role: 'admin'`). Status mutation must be strictly constrained to `role: 'customer'`.
- `[REQUIRED]` Zero-Cascade Deactivation: Deactivating an account must strictly freeze access. It must **never** cancel historical orders, modify financial/payment records, release inventory, erase reviews, or delete addresses/carts.
- `[REQUIRED]` Dedicated, RESTful Admin Customer Endpoints: Implement `GET /api/v1/admin/customers`, `GET /api/v1/admin/customers/:customerId`, and `PATCH /api/v1/admin/customers/:customerId/status` protected by the existing `authMiddleware` and `adminMiddleware`.
- `[NOT IMPLEMENTED / NOT REQUIRED]` Redis, BullMQ, Kafka, background workers, or separate cron jobs are not present and are **NOT REQUIRED** for P1.3.

## 2. Existing Architecture Overview

CommerceFlow API is an Express.js modular monolith backed by MongoDB and Mongoose with Zod schema validation.

```text
src/
├── common/
│   ├── errors/             # AppError, standard error shapes
│   ├── middleware/         # authMiddleware, adminMiddleware, validateRequest, rateLimiter
├── modules/
│   ├── users/              # User, Address models, controllers, validators
│   ├── orders/             # Order model, admin & customer controllers
│   ├── products/           # Product model, public & admin management
│   ├── cart/               # Cart model, guest-merge, pricing, coupon apply
│   ├── reviews/            # Verified buyer reviews, rating calculation
│   ├── wishlist/           # User wishlist items
│   ├── coupons/            # Coupon reservations & redemptions
│   └── payments/           # Razorpay order generation & webhook verification
└── routes/
    ├── admin.routes.js     # Mounts /api/v1/admin subrouters (orders, coupons, test)
    └── index.js            # Main route aggregator
```

### Authorization Flow:
1. `authMiddleware`: Extracts Bearer token, verifies JWT with `process.env.JWT_SECRET`, queries `User.findById(decoded.userId).select('-password')`. Checks `if (!user) throw 401`. Checks `if (user.isActive === false) throw 401 (ACCOUNT_DEACTIVATED)`. Attaches `req.user`.
2. `adminMiddleware`: Checks `if (req.user.role !== 'admin') throw new AppError('Forbidden: Admin access required', 403, [], 'FORBIDDEN')`.

All administrative endpoints are grouped under `/api/v1/admin` and protected by `[authMiddleware, adminMiddleware]`.

## 5. Authentication & Token Invariants

1. **Token Invalidation Mechanism:**
   - CommerceFlow uses stateless JWTs without server-side token storage.
   - However, `authMiddleware` queries `User.findById(decoded.userId)` on **every request**.
   - As a consequence, changing `user.isActive` from `true` to `false` takes effect **immediately** on the user's next HTTP request. There is no token expiration lag.
2. **Profile Endpoint (`GET /api/v1/users/me`):**
   - Protected by `authMiddleware`. If `isActive === false`, it returns `401 ACCOUNT_DEACTIVATED`.
3. **Admin Protection:**
   - Admin sessions also pass through `authMiddleware`.
   - An administrator who is deactivated will lose access on their next request.
   - Hence, preventing admin deactivation is critical to ensure continuity of system operations.

## 6. Admin Authorization Audit

- Centralized authorization via `adminMiddleware`:
  ```javascript
  const adminMiddleware = (req, res, next) => {
    if (!req.user || req.user.role !== 'admin') {
      throw new AppError('Forbidden: Admin access required', 403, [], 'FORBIDDEN');

    next();
  ```

- All new admin customer endpoints must be mounted onto the admin router with `adminMiddleware`:

## 7. Customer Listing Requirements

### Minimum Production-Grade Requirements:
1. **Pagination:** `page` (default: 1, min: 1), `limit` (default: 10, min: 1, max: 50).
2. **Status Filtering:** `status=active|inactive|all` (default: `all`).
3. **Role Filtering:** Constrained to `role: 'customer'` by default. Admin should be able to filter by `role=customer` (or view all customers). Administrators should not be mixed in with retail customers unless explicitly queried.
4. **Sorting:** `sortBy=createdAt|name|email` (default: `createdAt`), `sortOrder=asc|desc` (default: `desc`).
5. **Search Query (`search`):**
   - Must safely search `name` and `email`.
   - String sanitization: escape regex special characters (`[.*+?^${}()|[\]\\]`) to prevent ReDoS (Regular Expression Denial of Service).
   - Case-insensitive regex query on sanitized input: `{ $or: [{ name: { $regex: sanitized, $options: 'i' } }, { email: { $regex: sanitized, $options: 'i' } }] }`.

## 13. Critical Business Invariants & Impact Analysis

1. **Admin Accounts:**
   - Under no circumstances may an admin deactivate themselves or any other account with `role === 'admin'`.
2. **Orders & Fulfillment:**
   - Deactivating a customer does **NOT** cancel their active orders, does **NOT** restore inventory, and does **NOT** interrupt shipping. Fulfillment operates independently based on paid order contracts.
3. **Payments:**
   - Deactivating a customer does **NOT** issue refunds, alter Razorpay transactions, or modify payment receipts.
4. **Reviews:**
   - Deactivating a customer does **NOT** delete their published reviews or recalculate product star ratings.
5. **Cart & Wishlist:**
   - Cart and wishlist remain in the database untouched so if the account is subsequently reactivated, the customer's state is preserved.
6. **Authentication:**
   - Deactivated customers cannot log in, refresh tokens, access profile, add items to cart, or place orders.

## 14. Soft Delete vs Deactivation Analysis

- **Hard Delete (`DELETE /users/:id`):** `[FORBIDDEN]`
  - Violates foreign key references in Orders, Reviews, Addresses, Payment Webhooks, and Wishlist.
  - Destroys legal/financial audit trails.
- **Soft Delete (`deletedAt`):** `[NOT RECOMMENDED / UNNECESSARY]`
  - Introduces a second status field duplicating `isActive`.
- **Account Deactivation (`isActive: false`):** `[RECOMMENDED / EXISTING]`
  - Fully integrated with `authMiddleware`.
  - Reversible by admin.
  - Preserves 100% of data integrity and audit trails.

## 15. Search & Pagination Performance / Indexes

### Current Indexes on `User` Collection:
- `{ email: 1 }` (unique, lowercase)

### Index Assessment:
1. `GET /api/v1/admin/customers` queries typically filter by `role: 'customer'`, optionally `isActive`, and sort by `createdAt: -1`.
2. Without an index, sorting large collections by `createdAt: -1` requires an in-memory sort (`Btree / COLLSCAN`).
3. Proposed Indexes:
   - `{ role: 1, createdAt: -1 }`: Optimizes list sorting when role is filtered.
   - `{ role: 1, isActive: 1, createdAt: -1 }`: Optimizes filtered list by active/inactive status.
   - Compound index storage cost is minimal on the user collection and prevents memory exhaustion at 100k+ users.

## 16. Concurrency Strategy

- Admin status updates must avoid race conditions where two admins update the user concurrently.
- Implementation must use an atomic Mongoose/MongoDB update:
  ```javascript
  const updatedUser = await User.findOneAndUpdate(
    { _id: customerId, role: 'customer' },
    { $set: { isActive } },
    { new: true, runValidators: true }
  ).select('-password');
  ```
- If the document does not exist, the controller checks whether the target is an admin (returns 403 `ADMIN_ACCOUNT_PROTECTED`) or genuinely nonexistent (returns 404 `CUSTOMER_NOT_FOUND`).

## 33. Production Risks & Mitigation Matrix

| Identified Risk | Severity | Mitigation Strategy |
| :--- | :---: | :--- |
| Deactivating an admin locks out management | **HIGH** | Explicit rejection in validator and controller if target user has `role === 'admin'` or matches `req.user._id`. |
| Inactive customer logging in | **MEDIUM** | Add explicit `if (!user.isActive) throw 401` check in `login-user.controller.js`. |
| ReDoS via regex search query | **MEDIUM** | Escape special regex characters in search parameter before building query. |
| In-memory sorting on unindexed fields | **LOW** | Add compound indexes `{ role: 1, createdAt: -1 }` and `{ role: 1, isActive: 1, createdAt: -1 }`. |
| Unintended order/cart deletion | **CRITICAL** | Strict zero-cascade rule. Deactivation is a single-field update (`isActive: false`). |
